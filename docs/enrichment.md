# 情报富化设计

富化层负责把采集到的英文、非结构化漏洞情报加工成可检索、可比较的中文结构化知识，并建立文章、论文与漏洞之间的确定性关联。

## 1. 三级处理管线

| 阶段 | 目标 | 主要手段 |
|---|---|---|
| L1 AI 相关性判定 | 从全量情报中筛出 AI 安全相关条目 | 规则词预筛 → 包名白名单 → LLM 语义复核 |
| L2 确定性富化 | 提取可结构化的事实字段 | CPE 解析组件、GitHub Advisory 解析版本区间、正文正则抽取 CVE 与组件名 |
| L3 LLM 深度抽取 | 生成中文摘要与研判字段 | 中文摘要、15 类攻击类型、实体五元组、修复建议 |

设计原则：能用确定性规则完成的处理不引入 LLM；所有字段级处理保持幂等，空值视为待处理，重跑只补空缺。

## 2. 结构化字段

| 字段 | 说明 |
|---|---|
| `summary_zh` | 中文摘要：漏洞机制、影响范围、攻击后果 |
| `attack_type` | 15 类攻击类型归一 |
| `ai_subcategory` | AI 安全子类标签 |
| `affected_component` | 受影响组件或产品 |
| `affected_versions` | 受影响版本区间与修复版本 |
| `cpes` | CPE 资产标识 |
| `remediation_zh` | 修复建议 |
| `exploitability_note` | 可利用性说明（KEV/EPSS/攻击条件） |

## 3. 版本区间

从漏洞描述与厂商公告中抽取受影响版本边界；回填前执行防编造校验：版本号必须能在原文中找到，否则拒收。

## 4. 确定性缝合表

跨文档关联不依赖向量相似度，而是在富化阶段从正文抽取结构化标识：

- `article_cve`：文章正文中出现的 CVE 编号；
- `paper_link`：论文与受影响组件的关联。

问答侧通过 `/related` 接口按 CVE 或组件反查关联表，返回精确命中的文章与论文。

## 5. 质量闸门

- LLM 产出中的 CVE 编号必须能在库内找到；
- 验证码、WAF 拦截页在写入端拒收；
- 攻击类型统一映射到 15 类词表；
- 摘要、实体、修复建议的空值率纳入质量检查；
- 文章与 CVE 的关联必须来自正文抽取，不接受模型推断。
